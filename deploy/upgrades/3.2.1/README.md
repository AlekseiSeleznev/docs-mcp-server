# Применение миграций 3.2.1

`migrate.cjs` применяет два проверенных SQL-файла upstream в одной транзакции.
Наша миграция `015-add-page-publication-metadata.sql` сохраняет имя и историю.
Новые nullable-поля не требуют переноса данных, пересоздания эмбеддингов или
`VACUUM`. Штатный запуск приложения выполняет `VACUUM` после любых новых
миграций; для большого рабочего индекса этот шаг значительно удлиняет запуск.

Перед применением нужны проверенная резервная копия, сохранённый прежний образ,
остановленные задания и остановленный worker. Используются зависимости и SQL
из того же проверенного Docker-образа, который будет запущен после обновления.
Секреты и параметры подключения скрипту не передаются.

Из `/app` внутри контейнера с подключённым томом индекса:

```sh
node /upgrade/migrate.cjs /data/documents.db /app/db/migrations
node /upgrade/migrate.cjs /data/documents.db /app/db/migrations --apply
```

Первый вызов проверяет историю и контрольные суммы SQL. Второй применяет только
`015-add-progress-pages-indexed.sql` и `016-add-content-url-to-pages.sql`.
Неожиданные миграции и изменённые SQL-файлы приводят к отказу. Повторный запуск
сохраняет уже применённую схему. Ошибка второго SQL откатывает первый SQL и
обе записи истории в той же транзакции.

После применения запускаются worker и остальные сервисы. Их штатный runner
видит записанную историю и пропускает повторную миграцию и `VACUUM`.

Проверки скрипта на существующей базе из fixture: dry run, применение,
повторное применение, сохранение документов и атомарный откат при конфликте
второй миграции.

## Откат образа

`rollback.py` читает защищённый `state.json`, сверяет контрольные суммы текущего
Compose, прежнего Compose и `.env.worker`, проверяет наличие прежнего образа.
Пути берутся из локальных параметров подключения оператора. Секреты не выводятся.

```sh
python3 rollback.py "$DEPLOYMENT_DIR" "$RELEASE_DIR"
python3 rollback.py "$DEPLOYMENT_DIR" "$RELEASE_DIR" --apply
```

Первый вызов только проверяет готовность. Второй останавливает четыре основных
сервиса, возвращает сохранённый Compose и запускает прежний образ. Индекс,
артефакты, worker environment и отдельный OAuth gateway сохраняются. При ошибке
запуска скрипт возвращает Compose, действовавший перед его вызовом.

Этот путь подходит для проверенной совместимой схемы с двумя nullable-полями.
После запуска нужны авторизованный MCP-поиск, проверка артефактов, веб-интерфейса
и OAuth: TCP healthcheck сам по себе не подтверждает работоспособность поиска.

## Восстановление снимка данных

Защищённый каталог выпуска сохраняет `pre-cutover/documents.db`, его SHA256,
`compose.before.yml` и идентификатор прежнего образа. SQLite backup API учитывает
WAL. Финальная проверка `data_version` после остановки сервисов подтверждает,
что между снимком и переключением не появилось новых записей.

Если требуется возврат именно к данным перед обновлением, все writers сначала
останавливаются. Снимок проверяется по сохранённому SHA256, копируется в новый
том с прежними владельцем и правами и запускается с прежним образом. Текущий
том сохраняется для разбора и переноса появившихся после обновления документов.
Старые `documents.db-wal` и `documents.db-shm` к восстановленному файлу не
подключаются. Каталог `artifacts` остаётся на исходном томе, смонтированном только
для чтения. Переключение восстановленного индекса допускается после сравнения
количеств строк и функциональной приёмки.
