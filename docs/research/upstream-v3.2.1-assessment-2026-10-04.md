# Обновление нашего Docs MCP до upstream 3.2.1

Проверено 4 октября 2026 года, около 18:48 МСК.

Обновление технически осуществимо через объединение upstream с нашим fork и
проверку собственного Docker-образа на отдельной копии индекса. Текущая проверка
подтверждает совместимость добавляемых SQL-миграций и работоспособность исходной
версии. Совместимость всей объединённой программы ещё требует реализации и
приёмки.

В ходе исследования выполнены чтение репозитория и работающего сервера,
`git fetch`, пробное слияние через `git merge-tree`, локальные тесты и эксперимент
на синтетической SQLite-базе. Рабочая ветка, код приложения, серверные настройки
и содержимое производственной базы не изменены. Создан только этот отчёт.

## Что даёт обновление

- 3.0.1 исправляет формат ответа embeddings для OpenAI-совместимых провайдеров.
- 3.1 добавляет фильтры URL в `scrape_docs`, исправляет отдельные случаи
  `llms.txt` и нулевой глубины обхода.
- 3.2 исправляет сохранение и обновление страниц, обработку HTML и Markdown,
  выбор версий библиотек, разбор названий embedding-моделей и счётчики обхода.
  Добавляет обслуживание свободного места SQLite.
- 3.2.1 исправляет добавление HTTP-заголовков через веб-интерфейс при обычном HTTP.

Для нас основная ценность находится в 3.2.0. Переход включает накопленные
исправления после 3.0.0. Node 22 и текущие модели поиска сохраняются.

Эти числа описывают момент проверки и должны быть повторно зафиксированы перед
внедрением. Полная проверка целостности рабочей базы сейчас не запускалась.

У четырёх основных контейнеров одинаковый image ID:
`sha256:e8a1b2823fa30b2ef9bd3e4c0673fb596ecb0eebc9ad5986e26796d3c55bd79f`.
Registry digest существует, но метки `org.opencontainers.image.revision` нет.
Image ID не заменяет registry manifest digest. Точный исходный Git SHA
производственного образа по этим данным установить нельзя.

`docker diff` не обнаружил изменений под `/app/dist`, `/app/db/migrations`,
`/app/src` и в package-файлах у пяти сервисов. SHA-256 работающего
`/app/dist/index.js` worker:
`f6f6b7c815b1c7269fcfd116d0daf56ee6cf69e30dc0157e16bd52067e654f3f`.
Для нового выпуска нужно явно зафиксировать связь Git SHA → образ → registry
manifest digest. Предыдущие образы и конфигурацию следует сохранить для отката.

## Пересечения с нашими доработками

Проверка `git merge-tree --write-tree --name-only HEAD v3.2.1` завершилась с
кодом 1: 23 конфликтующих пути. Из них 7 относятся к программе и её тестам,
16 — к удалённым у нас OpenSpec-адаптерам в `.claude` и `.github`.

| Файл / область | Требуемое решение |
|---|---|
| `src/store/DocumentRetrieverService.ts` | Сохранить reranking, стабильный порядок при равных оценках, восстановление базовой выдачи при сбое и безопасные логи. Добавить нормализацию версий upstream; возвращать и `publication`, и `contentUrl`. |
| `src/store/DocumentStore.ts` | Объединить `publication_metadata` и `content_url` в SQL, типизированных параметрах и всех вызовах вставки. Сохранить наш отбор векторных кандидатов и read-only режим. Учесть новый путь `addEmptyPage`. |
| `src/store/types.ts` | Оставить оба поля метаданных и добавить новые структуры upstream. |
| `src/tools/SearchTool.ts` | Сохранить Matched/Related Artifacts и обработку ошибок без чувствительных деталей. Проверка exact version остаётся внутри нашей защищённой обработки ошибок; не дублировать её из конфликтного блока upstream. |
| `src/store/assembly/strategies/HierarchicalAssemblyStrategy.test.ts` | Согласовать тестовые объекты с обеими группами полей. |
| `package.json` | Сохранить MCPB/OAuth/reranking-команды; взять новую команду `test:live` и версию 3.2.1. |
| `vite.config.ts` | Сохранить точку сборки OAuth gateway и тесты из `tests/`; принять изменения настройки live-тестов. |

Автоматически объединённые места также требуют проверки поведения:

- `src/mcp/mcpServer.ts`: остаются наши инструменты артефактов, MCP resources,
  аннотации и разделение read-only/admin; добавляются фильтры upstream.
- Цепочка scraper → `DocumentManagementService` → store: сохраняются авторы и
  год при записи, refresh, смене представления страницы и возврате результата.
- Новый `content_url` должен проходить через SQL-поиск, сборку результата и
  отображение источника. По чтению кода 3.2.1 `findByContent` не выбирает это поле
  в поисковых SQL-запросах, хотя оно уже используется в типах и сборщике.
  Наш `src/mcp/utils.ts` также печатает только `result.url`. Нужна сквозная
  проверка страницы, доступной только по адресу Markdown-представления:
  отображаемая ссылка использует `contentUrl ?? url`, внутренняя идентичность
  страницы и сопоставление артефактов остаются корректными.
- `test/docker-e2e.test.ts:713`: текущий тест разрешает изменение только
  `pages.publication_metadata`. После обновления меняются также `pages.content_url`
  и `versions.progress_pages_indexed`; ожидания схемы нужно расширить адресно,
  сохранив проверки количества строк и ранее сохранённых данных.
- Старые OpenSpec-адаптеры остаются удалёнными. Upstream дополнительно приносит
  `.agents/skills` и `.agents/workflows`: их следует проверить, чтобы обновление
  приложения не вернуло удалённый рабочий процесс. Проектные правила Node 22,
  обращения с секретами и подключения к серверу сохраняются.

Официальный Docker-образ upstream не содержит наших Voyage-доработок,
Source Artifacts, publication metadata и Claude-интеграций. Для выпуска нужен
образ, собранный из объединённого исходного кода нашего fork.

## Миграции базы

Сохраняются точные имена трёх файлов:

1. `015-add-page-publication-metadata.sql` — уже применённая наша миграция.
2. `015-add-progress-pages-indexed.sql` — новая колонка версии из upstream.
3. `016-add-content-url-to-pages.sql` — новый адрес получения содержимого.

Совпадение числового префикса допустимо: `applyMigrations.ts` хранит полное имя
файла в `_schema_migrations`, сортирует имена и применяет только отсутствующие.
Переименование уже применённого файла заставит считать его новой миграцией
и повторить `ADD COLUMN`, что приведёт к ошибке.

Одноразовый эксперимент использовал настоящий `applyMigrations`, собранный из
нашего исходника, `better-sqlite3`, `sqlite-vec`, старую схему с синтетической
страницей, метаданными публикации и вектором размерности 1024. Затем в отдельный
каталог миграций добавлены два файла из целевого Git-тега.

| Эксперимент | Результат |
|---|---|
| Обновление существующей схемы fork | PASS |
| Создание пустой БД полным объединённым набором миграций | PASS |
| Повторный запуск миграций | PASS |
| Сохранение строк документов и метаданных публикации | PASS |
| Сохранение схемы 1024 и хеша векторов | PASS |
| Новые поля старых строк имеют `NULL` | PASS |
| Число зарегистрированных миграций после обновления | 18 |

Это проверка схемы на синтетических данных. Время миграции производственного
объёма и запуск объединённого приложения на его копии ещё не измерены.

После применения миграций существующий runner выполняет `VACUUM`. Для рабочей
БД около 6,17 GiB это может увеличить время запуска. Перед внедрением требуется
консистентный снимок SQLite с учётом WAL и измерение миграции на защищённой копии.
Простое копирование одного `documents.db` при работающем writer не является
проверенным резервным копированием. Новые миграции добавляют поля; обязательной
полной переиндексации из их SQL не следует. Изменения очистки и идентификации
страниц начинают влиять на содержимое при последующем scrape/refresh.

## Порядок внедрения

1. Сохранить текущие доработки в Git после проверки допустимого состава файлов.
   Зафиксировать исходный SHA, включая сегодняшний `rerank-3-lite` и Vanessa.
   Создать отдельный worktree и ветку обновления от этого снимка.
2. Объединить точный upstream `f2938c4`; разрешить перечисленные конфликты.
   Добавить регрессионные проверки через публичные операции поиска, записи,
   refresh и MCP. Сохранить текущие модели и конфигурацию безопасности.
3. На Node 22 выполнить `npm ci`, lint, typecheck, сборку, весь обычный набор
   тестов и Docker E2E; подтвердить проверки CI для итогового SHA.
   Проверить MCPB и OAuth, новые upstream E2E для версий,
   Markdown identity, пустых страниц, progress и неподдерживаемого содержимого.
4. Собрать собственный образ. Развернуть отдельный стенд с отдельными volumes,
   портами и защищённой консистентной копией production. Измерить миграцию,
   проверить целостность, размеры векторов, историю миграций, количества строк,
   publication metadata и хеши артефактов. Второй worker к рабочему тому не подключать.
5. Сравнить старый и новый поиск на одном снимке и одном наборе запросов.
   Для текущего 40-вопросного ONEC-набора: отсутствие ухудшения MRR/nDCG@5/Recall@30,
   MRR и nDCG@5 не ниже 0,90, сохранение точной базовой выдачи при принудительном
   сбое Voyage. Проверить задержку и дополнительные запросы 1C/SAP/Vanessa,
   авторов/год, Matched/Related Artifacts и выдачу исходных файлов.
6. До переключения подготовить и проверить восстановление старого образа с
   резервной копией данных. Зафиксировать registry digest обоих выпусков,
   Compose, защищённые настройки, том артефактов и отдельное состояние OAuth.
   Сохранение секретов выполняется штатным защищённым механизмом, вне Git и отчётов.
7. В согласованное окно остановить новые операции импорта/refresh и завершить
   активные задания. Получить финальную консистентную резервную копию. Запустить
   единственный новый worker, дождаться завершения миграций и проверки схемы,
   затем переключить web и оба MCP на тот же проверенный digest. Одного TCP
   healthcheck недостаточно для подтверждения готовности поиска.
8. Проверить авторизованные MCP initialize/list/search, read-only allowlist,
   Source Artifacts, веб-интерфейс, старый Bearer-вход и Claude OAuth gateway.
   У gateway отдельный образ и volume: его существующее состояние сохраняется;
   необходимость пересборки определяется проверкой совместимости.
9. После приёмки возобновить загрузки. Сначала проверить refresh одной
   представительной библиотеки, поскольку новые правила URL/Markdown могут
   объединять страницы. Массовый refresh отделить от обновления программы.

Возврат одного старого образа после записи новых данных не является доказанным
откатом. Гарантированный путь — восстановление согласованной пары старый образ
и предшествующий снимок данных. Для быстрого отката на уже мигрированной базе
нужен отдельный успешный тест старого образа на её копии.
