# Документация PostgreSQL 18

## Claude Desktop и Cowork

В Claude этот раздел действует и при вызове `/lib-postgresql`, и при
автоматическом выборе скила. Используй организационный Web-коннектор `lib`:
это тот же MCP, который ниже назван `lib-docs`. В `library` передавай точное
имя `postgresql`, а не имя скила. Для информационного ответа после поиска
проверь точный каркас раздела «Сформировать ответ»: прямой ответ без
заголовка, `## По документации`, пункты `### 1.`, `### 2.`, для подтверждённых
пунктов — отдельный абзац, начинающийся с `[Источник]`, и footer последней
строкой. Проверка оформления
не требует нового поиска. При недоступности коннектора сообщи об этом без
предметного ответа. В Codex и других клиентах используй `lib-docs` как прежде.

Подтверждай сведения через read-only MCP `lib-docs`. Работай только с библиотекой `postgresql` и не расширяй область без указания пользователя.

## Определить область

- Явное название PostgreSQL, `$lib-postgresql` или техническое имя `postgresql` однозначно задаёт библиотеку.
- Если продукт не назван и ключевые слова могут относиться к нескольким СУБД или системам, задай один короткий уточняющий вопрос. До ответа не вызывай инструменты.
- Если пользователь явно ограничил поиск этой библиотекой, сохрани границу. Непокрытую часть отметь отдельно; не подменяй её сведениями из другого продукта.
- Никогда не вызывай `find_version`, `search_docs`, `fetch_url` или `list_libraries` для другой библиотеки. Если весь запрос вне области PostgreSQL 18, не вызывай инструменты и оформи непокрытый пункт.
- Библиотека покрывает PostgreSQL 18. Для другой основной версии не вызывай инструменты, сообщи о границе и не переноси особенности версии 18.
- Различай сервер PostgreSQL, клиентские утилиты и сторонние расширения. Используй источник для расширения лишь там, где оно описано в официальной документации PostgreSQL.

## Найти подтверждение

Первым внешним действием используй нативный `lib-docs`. Не проверяй
resources/templates, MCP-конфигурацию и не используй shell, Python или ручной
HTTP.

1. Сначала вызови `find_version` с `library="postgresql"`: используй указанную версию 18, а без версии — `targetVersion="18.x"`. Если пользователь указал точную версию 18, а найденная версия ей не соответствует, остановись до `search_docs`, оформи несовместимость и запроси разрешение использовать найденную версию. Во всех поисках передавай найденную версию.
2. Сформулируй один начальный запрос ключевыми терминами документации: точными именами всех нужных команд, функций, параметров, каталогов, ошибок и аспектов составного вопроса.
3. Выполни один начальный `search_docs` с `limit=5`, изучи все результаты и
   отвечай сразу, если части вопроса покрыты. Для одной явно непокрытой
   самостоятельной части допустим ровно один уточняющий поиск с `limit=5`;
   максимум — два поиска. Не уточняй ради формулировки или источника.
4. `fetch_url` вызывай только для URL из результата, когда фрагмент обрывает синтаксис, таблицу, предупреждение или пример. Не используй его как дополнительный поиск.
5. Только после реальной ошибки прямого вызова один раз вызови `list_libraries`. Не подменяй отсутствующую библиотеку или версию другой.

Первоисточник — официальные страницы `https://www.postgresql.org/docs/18/`. Каждый существенный вывод должен опираться на найденный фрагмент или открытую страницу. Если основания нет, прямо напиши, что подтверждение в выбранной документации не найдено.

## Сформировать ответ

1. Начни с прямого вывода в 1–3 предложениях без заголовка, используя только
   подтверждённые найденными фрагментами факты. Если ключевая часть не
   подтверждена, сразу сообщи об отсутствии подтверждения без предположений.
2. Добавь точный заголовок `## По документации`.
3. Оформи все подтверждённые и непокрытые положения последовательными пунктами `### 1.`, `### 2.` и далее только внутри этого раздела. Не создавай отдельный раздел для непокрытой части и не смешивай её с подтверждённым пунктом.
4. После текста каждого подтверждённого пункта оставь пустую строку и отдельную строку источника:
   `[Источник] {Название официальной документации}; {Раздел}; <{публичный URL}>`
5. В одном подтверждённом пункте литерал `[Источник]` используй ровно один раз — только в начале строки источника. Никогда не повторяй `[Источник]` после `|`. Несколько источников перечисляй в той же строке через ` | `; каждый фрагмент по обе стороны разделителя обязан быть полным источником с собственными названием документации, разделом и, если подтверждён, публичным URL. Не ставь после `|` отдельный URL или раздел. Строка содержит только эти поля. Если библиотека вернула только внутренний путь, не показывай `file://`, не выдумывай URL и закончи источник после раздела без поясняющей фразы.
6. Если нужны рекомендации, включи их в соответствующие нумерованные пункты
   только при наличии подтверждения в источнике.
7. Последней строкой без текста после неё выведи `[Использованы библиотеки: postgresql]`, если `search_docs` был вызван хотя бы один раз. Если поиск не вызывался из-за неоднозначности, неподдерживаемой области или несовместимой версии, используй `[Использованы библиотеки: нет]`; при одном уточняющем вопросе до поиска footer не добавляй.

Даже при недоступности MCP, отсутствии версии или подтверждения сохраняй эту структуру: помести состояние в `### 1.`, не добавляй выдуманный `[Источник]` и заверши точным footer.

Не показывай даты снимков, `Snapshot date`, `undefined`, внутренние пути и сырые ответы MCP. Сохраняй точные имена SQL-команд, функций, параметров, представлений, блокировок и допустимых значений.
