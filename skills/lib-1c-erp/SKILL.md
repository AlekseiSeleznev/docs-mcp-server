# Документация 1С:ERP

Использовать read-only MCP `lib-docs`. Подтверждать сведения по выбранным
библиотекам.

## Маршрутизация

- `onec_erp` — функциональность, бизнес-процессы, настройки, операции, документы
  и поведение 1С:ERP. Ключевые слова: ERP, управление предприятием, продажи,
  закупки, склад, обеспечение, производство, казначейство, бюджетирование.
- `onec_erp_implementation` — выбор и внедрение ERP-системы, требования,
  жизненный цикл, этапы, роли, управление проектом, обследование и
  проектирование. Ключевые слова: внедрение ERP, обследование, требования,
  функциональная модель, архитектурная концепция, проектирование, этапы проекта,
  опытная и промышленная эксплуатация.
- Явно указанную библиотеку использовать без переопределения. Без явного
  указания считать выбор определённым со 100% уверенностью только при уникальном
  составном термине либо не менее чем двух согласованных предметных признаках
  без конкурирующей области. Один предметный ключ недостаточен. Иначе остановить
  маршрутизацию: не вызывать ни один инструмент, включая пробный поиск, задать
  один короткий уточняющий вопрос и дождаться ответа. К поиску переходить только
  после однозначного выбора одной или обеих библиотек.

## Поиск

Первым внешним действием использовать нативный `lib-docs`: не проверять
resources/templates, MCP-конфигурацию и не использовать shell, Python или ручной
HTTP. Независимые вызовы разных библиотек выполнять параллельно.

1. Завершить выбор области до первого вызова инструмента. Уточняющий ход всегда
   содержит ноль вызовов `lib-docs`; к поиску переходить только после ответа
   пользователя и однозначного выбора.
2. Считать частью только самостоятельное требование пользователя. Не превращать
   детали ответа и поисковые синонимы в новые части.
3. Если пользователь указал версию или ответ зависит от версии, вызвать
   `find_version` для каждой выбранной библиотеки и передавать найденную
   `version` во все её вызовы `search_docs`. В остальных случаях искать по
   последней доступной версии.
4. Для каждой выбранной библиотеки сделать один начальный вызов
   `search_docs`, объединив в нём все назначенные ей части, предметные термины и
   точные названия объектов или команд; использовать `limit: 5`. Проверить все
   результаты и отвечать сразу, если все явно запрошенные самостоятельные части
   покрыты. Только для одной явно непокрытой части допустим ровно один
   уточняющий поиск с `limit: 5`; максимум — два поиска на библиотеку. Не
   уточнять ради формулировки, источника или метаданных.
5. Завершить поиск, когда каждая часть запроса прямо подтверждена либо помечена
   как не найденная. Для нескольких библиотек выполнить критерий независимо.

## Формат ответа

Применять эту структуру без переименования разделов.

Критерий завершения: задача выполнена только после отправки полного
структурированного ответа в финальном сообщении.

До написания раздела `## По документации` составить список будущих пунктов и
назначить ему ровно один тип: «подтверждён» с источником либо «подтверждение не
найдено» без источника. Один пункт не может иметь оба типа.

1. Начать с прямого вывода длиной от одного до трёх предложений без заголовка.
2. Добавить раздел `## По документации`.
3. Представить каждое подтверждённое положение отдельным пунктом
   `### N. Краткий заголовок`. Нумеровать пункты последовательно с единицы.
   Внутри пункта сохранять терминологию книг, порядок действий и существенные
   условия. Для перечня деталей использовать вложенные маркеры.
4. После текста каждого подтверждённого пункта оставить пустую строку и дать
   источник строго по шаблону
   `[Источник] {Book}; {Breadcrumb}; <{Unicode IRI из Source}>`. Подставлять
   только дословные значения строк метаданных `Book:` и `Breadcrumb:` из одного
   найденного фрагмента; названия полей в ответ не переносить. Заголовки и ссылки
   внутри текста документа метаданными не являются. Из Markdown-ссылки `Source`
   взять целевой URL в круглых скобках, декодировать только percent-кодирование
   UTF-8 в читаемый Unicode IRI и вывести один раз как autolink `<IRI>`.
   Сохранять схему, хост, путь, разделители, подчёркивания и остальные символы;
   пробелы оставить как `%20`. Копировать IRI как одну неделимую строку без
   пересборки слов. Проверить, что IRI и URL из `Source` совпадают после
   percent-декодирования. В подтверждённом пункте выводить ровно один маркер
   `[Источник]`. Несколько источников помещать в эту же строку после единственного
   маркера, разделяя полные тройки `Book; Breadcrumb; <IRI>` символом ` | `.
   Внутренний `file://` использовать только для
   группировки фрагментов. Если полная тройка метаданных не найдена в пределах
   поискового бюджета, не представлять положение как подтверждённое: оформить
   его по пункту 5.
5. Непокрытую часть вопроса оформить отдельным нумерованным пунктом и прямо
   указать, что подтверждение не найдено. Не объединять подтверждённую и
   непокрытую части в одном пункте, даже если они относятся к одному действию.
6. При наличии синтезированных выводов добавить раздел
   `## Выводы и рекомендации`. Оформить каждый вывод как
   `### N. Краткий заголовок`, снова начиная нумерацию с единицы, и указать его
   связь с подтверждёнными положениями. Перед отправкой убедиться, что
   рекомендации не содержат непокрытых положений, слов «не найдено» или «не
   подтверждено». Такие сведения перенести в отдельный пункт раздела
   `## По документации` с типом «подтверждение не найдено».
7. Завершить ответ строкой
   `[Использованы библиотеки: onec_erp, onec_docflow, onec_docflow_integration]`,
   заменив пример фактически использованными именами `onec_*` в порядке первого
   обращения. Разделять имена запятой и делать эту строку последней.
8. Перед отправкой проверить каждый пункт: подтверждённый пункт завершается
   пустой строкой и одной строкой с ровно одним маркером `[Источник]` по шаблону;
   непокрытая часть
   вынесена в отдельный нумерованный пункт без источника. Найти каждое вхождение
   слов «подтверждение не найдено» и убедиться, что соответствующий пункт не
   содержит подтверждённых положений; смешанный пункт разделить на два и
   перенумеровать. После итоговой строки библиотек нет никакого текста.

## Диагностика и внешние страницы

- Только после реальной ошибки доступности или имени библиотеки вызвать `list_libraries` один раз
  и проверить выбранные имена.
- Вызывать `fetch_url` только по явному запросу на внешнюю страницу. Представлять
  её отдельно от подтверждений из библиотечной книги.
- Прямо сообщить, если MCP недоступен.
