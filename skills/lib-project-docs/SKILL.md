# Проектная документация

Подтверждай сведения через read-only MCP `lib-docs`. Работай только с выбранными библиотеками `project-docs-*` из карты и не расширяй область без указания пользователя.

## Определить запрос

- Работай только после ручного вызова `$lib-project-docs`.
- Сохраняй границу проектной документации ЛЮВЕ, МАНЕ и Полюс. Непокрытую часть отмечай отдельно без поиска в `sap_process_navigator`, `onec_erp` или другой библиотеке.
- Вызывай `find_version`, `search_docs`, `list_source_artifacts`, `get_source_artifact` и диагностический `list_libraries` только для библиотек выбранного множества `L`.
- Библиотеки покрывают версию `1.0.0`. При несовместимой найденной версии запрашивай разрешение на её использование.

## Выбрать библиотеки

Перед выбором прочитай [карту библиотек](references/library-map.md). Это единственный источник технических имён, проектов, разделов, алиасов и порядка.

1. Точный slug выбирает одну библиотеку.
2. Клиент и раздел выбирают существующее пересечение карты.
3. Явное сравнение клиентов по одному разделу выбирает пересечения только для названных клиентов.
4. Несколько явно названных пар клиент–раздел выбирают их пересечения в порядке запроса.
5. Клиент без раздела либо раздел без клиента требует одного короткого уточняющего вопроса. Выведи только вопрос и остановись без вызова инструментов и footer.
6. Отсутствующее пересечение отметь как непокрытое. Соседний проект не используй.
7. Если после этих правил `L` содержит больше трёх библиотек, одним коротким вопросом попроси сузить область и остановись без вызова инструментов и footer.

Изоляция клиентов — обязательный критерий выбора: библиотека другого клиента входит в `L` только при явном сравнении или явной паре клиент–раздел.

## Найти подтверждение

1. Первым для каждой выбранной библиотеки вызови `find_version` с её техническим именем в параметре `library` и `targetVersion="1.0.0"`. Если пользователь указал совместимую `1.0.0` версию, передай её как target. Если найденная версия несовместима с запрошенной, остановись до `search_docs`, оформи несовместимость и запроси разрешение использовать найденную версию. Во все дальнейшие поиски и списки этой библиотеки передавай найденную версию. Вызовы `find_version` по выбранным библиотекам запускай параллельно.
2. Сохрани язык предметного запроса. Используй точные русские формулировки индекса, имена файлов и коды MSP или ERP. Не переводи запрос в английский и не добавляй машинный перевод.
3. Объедини независимые части запроса в один начальный поиск на каждую выбранную библиотеку. Первый и единственный начальный `search_docs` выполни с `limit=5`. Начальные поиски по выбранным библиотекам запускай параллельно. Изучи все результаты, включая их Process Card, Matched Artifacts и Related Artifacts, до следующего вызова.
4. После оценки всех начальных результатов распредели остаток бюджета `6 - |L|`. В каждом раунде дай по одному уточняющему поиску каждой библиотеке с неполным подтверждением: сначала в порядке пользователя, затем в порядке карты. В одной библиотеке допустимо не больше трёх поисков. Остановись, когда подтверждение достаточно, бюджет исчерпан либо каждая библиотека достигла своего предела. Для повторов используй только `limit=5` или `limit=10`; `limit=10` допустим лишь после оценки первого результата. Не пропускай библиотеку молча: исчерпание бюджета отметь как непокрытое.
5. Считай Matched Artifacts прямым основанием найденного Search Result. Related Artifacts принадлежат тому же разделу, но сами не подтверждают совпадение. Храни эти группы раздельно при обосновании ответа; итоговый список артефактов является инвентарём выбранного раздела, а не доказательством совпадения.
6. Перед итоговым списком вызови `list_source_artifacts` один раз для каждого подтверждённого раздела с точным набором `{library: slug, version: найденная для slug версия, processId: slug}`. Независимые вызовы запускай параллельно. Читай полный массив `structuredContent.artifacts`. Удаляй повторы по `artifactId` только внутри одного такого набора; одинаковые файлы разных клиентов сохраняй раздельно. Для `Missing` и `ExternalUnresolved` выводи краткую пометку `недоступен` и не запрашивай байты.
7. Не получай Source Artifact для обычного информационного ответа. Переходи к исходному файлу только когда пользователь прямо просит файл либо задачу невозможно надёжно выполнить без точных исходных байтов.
8. Когда пользователь просит конкретный файл, выбери соответствующую доступную запись. Для запроса скачать все файлы или все документы выбери все доступные записи `Downloaded` из полного дедуплицированного результата `list_source_artifacts`; недоступные записи пропусти с кратким пояснением. Затем выполни раздел `Скачать исходник`. Не принимай от пользователя путь сервера, абсолютный путь, `file://`, storage key или произвольный URI вместо `artifactId`.
9. Получай байты только через `get_source_artifact`: используй blob из его embedded resource и не заменяй этот вызов на `resources/read`. Не вызывай `fetch_url`, Chromium или browser и не используй локальный либо серверный исходный путь как альтернативный источник файла.
10. При ошибке доступности один раз вызови `list_libraries` только для диагностики. Не подменяй отсутствующую библиотеку, версию или артефакт другой библиотекой.
11. Для представления `xlsx-metadata` опирайся только на имена листов и выборку строк, а не на полную таблицу. Для `unsupported-metadata` не излагай содержимое исходника как прочитанный текст; исходник остаётся в инвентаре.

## Скачать исходник

1. Сначала определи папку назначения. Для указанной пользователем папки разверни `~`, разреши относительный путь от текущей рабочей папки и нормализуй его до абсолютного. Без указанного пути начни с текущей рабочей папки и иди вверх до ближайшего каталога, содержащего хотя бы один маркер проекта: `.git`, `package.json`, `pyproject.toml`, `Cargo.toml`, `go.mod`, `pom.xml`, `build.gradle` или `build.gradle.kts`; используй в нём `artifacts/project-docs/<проект>/<nn-slug>/`.
2. Если проектная папка не найдена, до получения исходных байтов задай один короткий вопрос о месте сохранения. Сообщи, что проектная папка не найдена, предложи рабочий стол как вариант по умолчанию и остановись до ответа.
3. Получи выбранные исходники только через `get_source_artifact`. Для двух и более артефактов запусти независимые retrieval-вызовы параллельно одним batch и дождись всех результатов.
4. После завершения всех retrieval-вызовов разреши путь `scripts/save-source-artifacts.mjs` относительно папки этого `SKILL.md` и запусти writer один раз для всех выбранных файлов:
   `node <skill-dir>/scripts/save-source-artifacts.mjs --destination <абсолютная папка> --count <количество>`
   В Codex сразу используй интерактивный режим, дождись активной сессии и JSON `{"ready":true}`.
5. Для каждого результата передай writer одну полную строку JSONL с полями `suggestedFilename`, `blob`, `sizeBytes`, `sha256`, `mimeType`. Bundled writer сам отключает echo и canonical PTY mode, проверяет base64, размер, SHA-256, формат, существующие файлы и коллизии, затем сохраняет через `create-new` без временных файлов и удаления.
6. Считай fast path завершённым, когда writer вернул по одной записи с `status` и абсолютным `path` для каждого выбранного артефакта и завершился с кодом 0. При первом сбое writer допустим один повтор той же команды; повтор безопасно переиспользует уже проверенные файлы. После второго сбоя остановись и сообщи блокер.

Используй только этот fast path. Не генерируй inline Python или альтернативный writer, не запускай диагностические sleep/probe-команды и не повторяй проверки, уже выполненные bundled writer.

Первоисточник — выбранные библиотеки `project-docs-*`. Существенные утверждения основывай только на найденных Search Results. Русский ответ излагает найденное подтверждение. Если основания нет, прямо напиши, что подтверждение в выбранной библиотеке не найдено.

## Сформировать ответ

1. Для информационного ответа начни с прямого вывода на русском языке в 1–3 предложениях без заголовка.
2. Добавь точный заголовок `## По документации`.
3. Оформи подтверждённые и непокрытые положения последовательными пунктами `### 1.`, `### 2.` и далее только внутри этого раздела. Не смешивай непокрытое положение с подтверждённым пунктом.
4. После текста каждого подтверждённого пункта оставь пустую строку и отдельную строку источника:
   `[Источник] Проектная документация {ЛЮВЕ, МАНЕ или Полюс}; {раздел или имя файла}`
5. В одном подтверждённом пункте литерал `[Источник]` используй ровно один раз — только в начале строки источника. Никогда не повторяй `[Источник]` после `|`. Несколько источников перечисляй в той же строке через ` | `; каждый фрагмент по обе стороны разделителя обязан быть полным источником с собственными названием публикации, разделом и, если подтверждён, публичным URL. Не ставь после `|` отдельный URL или раздел. Если библиотека вернула только внутренний путь, не показывай `file://`, не выдумывай URL и закончи источник после раздела без поясняющей фразы.
6. Если нужен синтез, добавь `## Выводы и рекомендации` с нумерованными рекомендациями, основанными только на подтверждённых пунктах.
7. Если выбранный раздел содержит Source Artifacts, в конце содержательной части добавь точный заголовок `## Артефакты`. Сначала создай группы в порядке каталожных типов: `Document` — `Документы`, `Spreadsheet` — `Таблицы`, `Presentation` — `Презентации`, `Plan` — `Планы проекта`. При нескольких разделах внутри каждой группы раздели записи обычными строками `<Клиент> — <Раздел>`. Оставь названия групп и разделителей обычным текстом без `[]`, заголовков Markdown и жирного выделения. Под разделителем либо сразу под группой выведи маркированным списком для `Downloaded` только `suggestedFilename`, а для недоступной записи — её `name` и `— недоступен`. Не выводи пустые группы, повторы внутри одного раздела, `Matched Artifacts`, `Related Artifacts`, технический статус, формат или размер и не показывай `artifactId` в ответе.
8. Если сохранён один или несколько файлов, добавь строку `**Скачано**`, а ниже выведи по одной строке `имя файла → полный путь` в виде локальной Markdown-ссылки Codex: `- [имя файла](<абсолютный путь>)`. Используй одну ссылку на каждый сохранённый файл. Для любого локального target оберни target в `<...>`; пробелы оставь как есть и не экранируй круглые скобки внутри target. Когда запрос состоит только из скачивания — независимо от того, первый он или последующий, — не выводи разделы с документацией, выводами и инвентарём: ответь только блоком `**Скачано**`, кратко назови пропущенные недоступные записи при их наличии и добавь footer. Не показывай base64, сырые байты, внутренний путь источника, storage key, MIME, размер, SHA-256 или описание проверок.
9. Последней строкой без текста после неё выведи `[Использованы библиотеки: slug1, slug2]` с уникальными фактически вызванными именами в порядке запроса, затем карты. Если поиск начался, но ни одна библиотека не использована, выведи `[Использованы библиотеки: нет]`; при уточняющем вопросе до поиска footer не добавляй.

Перед началом скачивания дай не более одного короткого обновления: `Сохраняю {количество} файлов в {папка}`. Не сообщай о восстановимой внутренней ошибке или безопасном повторе, пока действие продолжается без участия пользователя. Сообщи технический блокер только если безопасные попытки исчерпаны и без действия пользователя продолжить нельзя.

Даже при недоступности MCP, отсутствии версии или подтверждения сохраняй эту структуру: помести состояние в `### 1.`, не добавляй выдуманный `[Источник]` и заверши точным footer.

Не показывай даты снимков, `Snapshot date`, `undefined`, внутренние пути, приватные адреса и сырые ответы MCP. Сохраняй имена файлов и коды документов как в каталоге.
